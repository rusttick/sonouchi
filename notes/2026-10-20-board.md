# The sprint session: the board, the stand-up and reframing (I1, I3, I4, I7)

Roughed out with the steps in `TODO.md`, section 2, on 2026-10-20.
This replaces the first draft of the same day, which put screen
positions into the task data (`:task/column`, `:task/rank`). The owner
stopped it before anything was decided.

A proposal for the owner's review. Nothing here is built, and no
attribute is named yet: the facts are described in words, and named
once the owner agrees them.

## The session

After the morning stand-up, the owner brings sonouchi into line with
the whiteboard. Everything that happens is one of two kinds of act:

- **a stand-up record** on one task: started, finished, worked on
  yesterday, waiting (I7)
- **a replacement of N tasks by M** (I3), which covers every change to
  what the tasks are:

  | Case    | N → M             |
  |---------|-------------------|
  | add     | none → some       |
  | drop    | some → none       |
  | split   | 1 → several       |
  | merge   | several → 1       |
  | reframe | several → several |

  Owner's observation, 2026-10-20: if a drop is some → none, an add is
  none → some, so adding needs no act of its own.

The working set is one sprint: the whiteboard covers only this sprint,
and the owner does not yet know how the whole backlog should be shown.
Until there is another view, there is one sprint, and it never ends
(owner, 2026-10-20). Every task is in it, so no sprint fact is needed
yet.

## The frame (V9)

The same for every action, always in the same places:

    sonouchi   STAND-UP          [ query                ]     12 of 31 tasks

- the action's name, large (V10)
- the query bar, top centre. Typing filters every column (dynamic
  queries, Ahlberg 1992), and the order of what is left is kept
  (`TODO.md`, "Decided"). Enter opens the replacement display with no
  old tasks and the query text as the first new title, so a task that
  was not found takes no retyping
- the count: the tasks shown, of all the tasks on the board

## Action 1: the stand-up, on the board

**1. The question.** Which tasks on the whiteboard have no record yet
today? (`ux-research-visual.md`, section 1.1.)

**2. The facts.** Reads each task's title, start, finish, waits and
days worked. Appends:

- started: the task, the day it started, and when that was recorded
  (Step 0: the actual start)
- finished: the same, for the finish (Step 0: the actual finish)
- worked on: the task and the day (`ux-research.md`, section 10,
  decided)
- waiting began and waiting ended: see "Waiting" below

Each records two times: the day it happened, and when it was recorded
(`ux-research.md`, section 10).

**3. The display.** The whiteboard's layout, so that moving from the
physical board to the screen needs no translation (visual momentum,
Woods 1984). Each column is a group computed from the facts, never
stored (I1):

| Column      | A task is here when                     |
|-------------|-----------------------------------------|
| To do       | it has not started                      |
| In progress | it has started and not finished         |
| Waiting     | it has a wait that has not ended        |
| Done        | it has finished                         |

To do, In progress and Done are Step 0's states. Waiting is the
owner's "blocked" column, and is a column (owner, 2026-10-20); see
"Waiting" below.

Within a column, the latest to arrive is at the top. This order is
computed from the times of the acts, so it changes only through the
owner's acts (V6), and nothing about screen position is stored. A
ranked order waits for the ranked list (I2, `TODO.md` section 4,
"Order").

Tasks with no record today are in full ink, and recorded ones are
lighter with a ✓ (V3, V8). A dot for each day worked is a hypothesis to
try (`ux-research-visual.md`, section 2.4).

**4. The acts.** A cursor moves over the cards with the arrow keys.
The mouse works too (V11), but there is no dragging between columns,
because a drag is slower and more error-prone than a key (MacKenzie
1991).

- `s` started: the card moves to In progress
- `f` finished: the card moves to Done
- `w` worked on yesterday
- `b` waiting: asks for the reason and for whom or what, in a small
  field on the card
- `x` marks the card for a replacement; `r` opens the replacement
  display with the marked cards, or the card under the cursor
- Escape leaves the action

Every act updates the card in place and marks it (V7, V12), and can be
undone (V13). Keys are shown next to the cursor (V11).

**6. The prediction.** About 1.55 s a task by key, M + K, so about 16 s
for ten (`ux-research-visual.md`, section 3.3).

## Action 2: replacing N tasks by M

**1. The question.** What replaces these tasks?

**2. The facts.** Appends one act: the new tasks with their titles and
states, and that each old task was replaced by the new ones. The
state of every new task is chosen before the act is recorded (owner,
2026-10-20). The
old tasks leave the board and stay in the record (I3). A drop is a
replacement by nothing, and is recorded, not erased (design 3, rule 3).
A task added by mistake is corrected with undo, not dropped.

**3. The display.** The old tasks on the left, and a text area on the
right with one new title per line, as in quick entry. A small chain
reads best as a node-link drawing or a before-and-after pair (V17); the
board's grouping by state does not help answer this question (V1), so
this is a display of its own, which keeps the selected tasks (V9).

    REPLACE                                       Esc cancel · ⌘Enter record
    measure spindle runout     →   order dial gauge holder
                                   measure runout at 3 speeds
                                   compare with the 2024 log

**4. The acts.** Type the new titles; ⌘Enter records the replacement
and returns to the board with the new cards marked (V7); Escape
returns without recording. Undo removes the new tasks and restores the
old ones in one step.

**6. The prediction.** A split into three: select, open and record are
four keystrokes and one mental step, about 2 s. The rest is typing
three titles, about 26 s for 25 characters each. Low viscosity (Green
1996) means the 2 s, since the typing cannot be avoided.

## Waiting

The owner's "blocked" column marks a task that waits on something
outside their control. What the research says:

- **Design 3 already records it, as a reason.** Step 0: "When a task
  starts later than its predecessors allow, the reason is recorded as a
  short category, such as 'waiting for a person', 'waiting for an
  outside party' or 'not in the plan'." Step 6 tests from these
  reasons how much delay came from waits outside the network (H6), and
  step 5 expects large overruns to go with reasons such as "an outside
  party" (H5b). So these waits are some of the most valuable facts the
  app can collect. They should be recorded with their times, not just
  shown.
- **A wait can begin after the start.** Step 0 asks for a reason only
  when a start is late, but the owner's tasks also wait in the middle.
  A wait while in progress is part of the elapsed duration that step 1
  measures, so it is recorded the same way: waiting began, with its
  reason and on whom, and waiting ended.
- **Waiting is not a state.** A waiting task has either started or not,
  and design 3 counts elapsed time from the start whether or not it
  waits. So the wait is recorded beside the state, never instead of
  it. The card shows which: "waiting, started 3 days ago".
- **It may be a request in the other direction.** A wait on someone
  outside usually means the owner asked them for something. That is a
  request with the owner as the asker: who was asked, in what words,
  any promise, and the report back (Winograd 1987, I6). Requests made
  to the owner and requests the owner makes are then one kind of
  thing. When the other side reports done, the wait ends. Their promise
  is a commitment, not an estimate (McConnell 2006, design 3 Gap 7),
  and can feed the forecast for the requests that wait on it. Record
  these as facts, without forcing every exchange through a protocol
  (Suchman 1993). This waits for the requests part (I6); for now a wait
  is a reason and a few words.

**A column, decided by the owner on 2026-10-20.** A column mirrors the
whiteboard (visual momentum), and is the strongest grouping cue (common
region, Palmer 1992). Each card says whether it has started. A mark in
place would have kept started and not-started tasks apart; both are
views of the same facts, so this can change after the trial.

## What a replacement does with each attribute

Open: the owner does not yet know how attributes should carry over
from N old tasks to M new ones, and wants to avoid having to fill in
every attribute of every new task. A way to think about it:

- **History is never copied.** Starts, finishes, days worked, waits
  and estimates are facts about the old tasks, and stay with them,
  reached through "replaced by". Copying them would record things that
  did not happen (design 3, rule 3). An estimate in particular must be
  made afresh, before the new task starts, and without the old one
  shown first, which would anchor it (Step 0, "Psychology").
- **What points at the old tasks must be pointed somewhere.**
  Dependencies, and later the requests a task serves, would otherwise
  be lost. The obvious default is that every new task gets all the
  links of all the old ones, shown, for the owner to prune. For N > 1
  this is the union.
- **Each attribute brings its own rule.** Copy, union, never, or ask:
  one table, in one place (CONTRIBUTING, section 6). Today there are
  only the title and the state, and the owner has decided that the
  state is chosen for each new task. Each later part that adds an
  attribute must add its row to the table before it is built.

## Open questions for the owner

1. How a replacement carries links over, above, once there are links.
2. The keys for the two acts below, "correct the wording" and
   "replace".

Decided on 2026-10-20: waiting is a column; the state of every new
task is chosen before a replacement is recorded; there is one sprint,
which never ends, until there is another view.

Decided on 2026-10-24:

- **A rename is a replacement, 1 → 1.** Something about the task has
  changed, so it needs a new estimate.
- **Correcting the wording is a separate act.** It fixes a typo or
  says the same thing better: the same task, with the same history and
  estimate, and a new title appended as a correction. The test for
  which act to use: would the estimate be different? If so, it is a
  replacement. Both titles stay in the record, so a correction that was
  really a change of meaning can be seen later.
- **Choosing each new task's state.** Each new line shows a state, with
  keys 1 to 4 to change it; the visible default counts as chosen. The
  default is the old task's state when N is 1, and To do otherwise.

**The old estimate as a default.** The owner suggested filling in the
old estimate as the new one's default. Design 3 and V14 both rule this
out: Step 0 shows no other estimate before a person enters theirs, to
avoid anchoring (Tversky 1974, Aranda 2005), and V14 says an estimate
field starts empty, with no default (Liu 2019 found that a starting
value pulls answers towards it). A prefilled old estimate is the
strongest anchor there could be, and an estimate that was only
accepted, not made, is not data step 1 can use.

Decided instead (2026-10-24): the field starts empty, and the old
estimate is not shown at all, before or after. Showing it afterwards,
as planning poker's reveal does, would invite a revision towards it,
which is the same anchoring one step later. Planning poker's reveal is
for several people to find out why they disagree; one person comparing
with their own old number learns nothing that way. The comparison that
teaches is design 3's step 1, which scores estimates against outcomes.
For the same reason, the old tasks on the left of the replacement
display show no estimates.

## Search

Search is the owner's main way of finding things, so it uses a prepared
index and an established tokenizer (decided 2026-10-20). The index is a
value in the core, `sonouchi.core.search`, not a JavaScript library:
those all keep a mutable index. It is a sorted map from term to task
ids, kept in the state and updated by each act, and a property test
checks that updating it gives the same index as building it afresh.

The tokenizer is passed in. The shell's follows Unicode word boundaries
(UAX #29) through the browser's `Intl.Segmenter`, the standard that ICU
and Lucene's StandardTokenizer implement.

A task matches when every typed word, in any order and any case,
starts a word of its title, allowing one typing mistake per five
letters, with the first letter right.

Measured on the JVM with 3,000 made-up titles: building the index 13
ms, updating it for one task 0.01 ms, a two-word search with typing
mistakes 2.4 ms. To measure again in a release build.
